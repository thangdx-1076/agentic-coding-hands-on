## CI-fix verdict: raising the timeout is the right fix, not a masked defect
Walked the challenge points directly:

1. **Is there a real defect in the click handling?** Traced `onClick={() => close(false)}` on both `<Link>`s: `close(false)` only calls `setOpen(false)` — no `preventDefault()`, no synchronous side effect that could block navigation. Next's `<Link>` composes the caller's `onClick` first, then (if not prevented) runs its own handler that intercepts the native click and drives the App Router's soft navigation via a router-level transition, not one tied to the clicked DOM node's continued existence. The panel unmounting a tick later (via the React state update) does not cancel an in-flight navigation that the router is already tracking. No evidence of a swallowed click.
2. **Root-cause discriminator, independently checked**: `.github/workflows/*.yml:82,156` hardcodes `NEXT_PUBLIC_SUPABASE_URL: "http://127.0.0.1:54321"` in the CI-safe job — this is a **permanent, deterministic property of that CI lane**, not transient flakiness. That makes the ~7.4s data-route cost a stable baseline, not a one-off noisy sample, which raises confidence that a 15s budget (~2× margin) is a deliberate, defensible choice rather than a guess.
3. **Would a real user on a slow connection see a broken click?** Yes, plausibly — the panel closes immediately (no pending/loading UI) while the destination route may take several seconds to paint on a slow connection or cold Supabase. Checked: there is no `loading.tsx` under `(public)/kudos` or `(public)/standards`, and no `useLinkStatus` anywhere in the app. This is a real UX gap, but it is **not introduced by this diff** — clarifications.md explicitly modeled "Viết KUDOS" on the precedent in `standards-footer-actions.tsx`, which has the exact same architecture (plain `<Link>`, no pending state) and predates this PR. Out of scope here; flagging only so it isn't lost.
4. **Established pattern comparison**: `home.spec.ts`'s own `[TC ID-2]` test also hits a data-backed route and takes 7.6s in the same CI run, yet never fails — because it uses `page.goto()` (default Playwright navigation timeout 30s) rather than `expect(page).toHaveURL()` (default 5s). The fix targets the actual mismatched budget (assertion-level `expect` timeout, not the page's own navigation timeout) with a scoped per-call override rather than a blanket `expect.timeout` bump in `playwright.config.ts` — correctly minimal blast radius.

**Verdict: the fix is correct, well-reasoned, and independently confirmed. No masked defect found.** One residual, non-blocking gap: this exact fix has only been verified locally (real Supabase, 3.1s) and against a simulated broken-Supabase run, not yet against a real CI run of the exact commit — recommend pushing and watching CI go green once before merge, since it's currently an uncommitted working-tree change.

## Edge Cases Turned Up
- **Focus-on-open via mouse click, re-verified as pre-existing, not new**: `useMenuKeyboardNav`'s `openMenuAt(0)` + the focus effect move DOM focus to the first menu item (`itemRefs.current[0]`) immediately after *any* open — including a plain mouse click, not just keyboard nav. Confirmed this is not new: `home.spec.ts:326-327`'s own comment ("Menu's `useMenuKeyboardNav` hook moves focus into first menuitem") documents this for the *account* menu using the identical hook, predating this PR. Not a regression.
- **Tab order with the DOM-order flip (menu now precedes trigger)**: traced concretely — when open, `item[0]` carries `tabIndex=0` (or `-1` if `activeIndex` moved), `item[1]` is `-1`, and the trigger `<button>` has no explicit `tabIndex` (default `0`). Native Tab order among same-value-`0` elements follows DOM order, so Tab from the focused `item[0]` advances to the trigger button next (item[1] is correctly skipped as `-1`). Pressing Tab also bubbles into the menu's own `onKeyDown` (`case "Tab": close(false)`), closing the panel without fighting the native focus move. No focus trap, no stranded focus.
- **Click-outside boundary vs. real navigation**: clicking either menuitem is "inside" `rootRef` (which wraps both the menu and the trigger), so the `mousedown`-based outside-click closer never double-fires against the link's own `close(false)`. No race.
- **`aria-haspopup="menu"` + `aria-expanded` + constant `aria-label`**: legitimate ARIA APG pattern (same accessible name across toggle states, state carried by `aria-expanded`), not a "test-passes-but-broken" case — this is how most native disclosure/hamburger-style toggles are built. `title={cancelLabel}` is correctly subordinate to `aria-label` in accessible-name computation (`aria-label` always wins), so it adds, at most, a redundant accessible *description* on some AT/browser combinations — not incorrect, just occasionally chatty. Not a defect.
- **Icon fidelity, verified byte-for-byte via `git diff`, not assumed**: `IconClose`'s single `<path d="M13.4759...">` and `IconSunLogo`'s 4 `<path>` + 2 `<linearGradient>` blocks are character-identical between the pre-extraction inline SVGs and the new standalone components. No drift introduced by the promotion.
- **Design numbers, recomputed independently against the shipped Tailwind classes** (not just re-read from `clarifications.md`): container `gap-5` = 20px ✓, `items-end` ✓; options `h-16`(64px)/`p-4`(16px padding)/`gap-2`(8px)/`rounded`(4px)/`bg-login-button`(#FFEA9E)/`text-login-button-text`(#00101A)/`font-montserrat text-2xl leading-8 font-bold`(24px/32px/700) all match node data; cancel button `h-14 w-14`(56px)/`rounded-full`/`bg-[#D4271D]` matches; total stack height `64+20+64+20+56=224` matches node `313:9140` exactly. No hardcoded-width regression on "Thể lệ" (intrinsic width, per the documented decision). The one known deviation (`right-6`=24px vs. design's 19px) is pre-existing from the homepage phase, unrelated to this diff, correctly out of scope.
