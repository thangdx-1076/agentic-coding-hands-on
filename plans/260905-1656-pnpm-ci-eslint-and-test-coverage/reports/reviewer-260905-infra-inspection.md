4. **Phase 03's core verification method for "whitespace-only" doesn't actually prove what it claims — though the underlying result checks out on manual review.** The report says: *"Verified with `git diff -w --stat` scoped to exactly the 17 files ... which returned empty output."* I ran the identical command against files that were untouched by any other phase (`components/login/google-login-button.tsx`, `icon-vn-flag.tsx`, `login-background.tsx`, `login-error-alert.tsx`, `next.config.ts`, `lib/supabase/proxy-client.ts`, `tests/e2e/visual-validation.mjs`) and got **non-empty** `git diff -w` output for every one of them (e.g. `login-error-alert.tsx`: 4 insertions / 1 deletion even under `-w`). This is because `-w` only ignores whitespace *within already-aligned lines*; Prettier's most common edit — wrapping one long line into several — changes the line count, so `-w` cannot collapse it back to "no diff." I manually read all 7 of these isolated diffs plus a large chunk of `tests/e2e/visual-validation.mjs`'s diff: every hunk is genuinely line-wrapping, quote-style (`'` → `"`), or trailing-comma changes — no identifier, literal, or logic token differs. **The underlying claim (whitespace/formatting-only) holds**; the reported proof method does not, and should not be relied on again for this class of check.
   - **Fix**: for future "prove it's formatting-only" gates, use `prettier --check` on the pre-image plus a build/typecheck/test rerun (already done here) rather than `git diff -w`, or diff AST-normalized output. Not blocking — already independently re-verified by hand in this review.

5. **The plan explicitly scoped the invalid-code `/auth/callback` test to `@auth`/local-only for a stated reason; the delivered test instead sits in the CI-safe path where that reason applies.** Phase 04's own Architecture section places `?code=<invalid>` under the local-only `Authenticated`/`@auth` block specifically because distinguishing "GoTrue rejected a bad code" from "the network is simply down" requires a reachable Supabase. The delivered test (`tests/e2e/login.spec.ts:322`, `[ROUTE001] GET /auth/callback?code=<invalid>...`) instead lives in the CI-safe `Unauthenticated` block (confirmed: not tagged `@auth`, listed in the 27-test `--grep-invert @auth` set). Tracing `app/auth/callback/route.ts:31-44`: when Supabase is unreachable (the CI default), `exchangeCodeForSession` fails on network grounds and the `catch` falls through to the exact same `/login?error=auth_code_error` redirect an actually-invalid code would produce. So in CI this test cannot tell "invalid code correctly rejected" apart from "Supabase was never reachable" — it passes for a reason unrelated to its stated intent, and is redundant with the two outage tests that already exercise this same fallback branch. It's not a false claim of coverage (the CI notice never claims the valid-code or exchange-rejection path is covered) and it's harmless, but it is exactly the "test that clears CI for the wrong reason" pattern this inspection was asked to hunt for, and it deviates from the plan's own risk analysis without that deviation being called out anywhere in the tester's report.
   - **Fix**: either move this test under `test.describe("Authenticated", { tag: "@auth" })` per the original plan (so it only proves something when Supabase is actually reachable), or add a one-line comment at the test noting it is CI-redundant with the outage tests and only discriminates real invalid-code rejection when run locally against `saa-app`.
